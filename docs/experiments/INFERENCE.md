# 推理适配：正确性先行，计时口径固定

本页总结 35B 两步教学控制权重的 vLLM 桥接、完整 8192 步补偿产物的自定义推理，以及 122B 自定义推理。各自的权重、实现和成绩分别记录。35B 实验适配器尚未合入根目录课程，122B 已发布的 `infer.py` 是自定义单请求引擎。

## 保留失败，解释修复

| 观察 | 定位/修改 | 后续证据与范围 |
|---|---|---|
| 35B 初始 vLLM 512-token 最终状态相对 L2 约 0.05045，超 0.005 | 对照 160 个记录点；同输入专家误差约 0.00023，前序输入变化可改变 38/512 token 的 top-8 集合 | 专家解包不是唯一原因，继续定位上游 |
| GDN 精度不一致 | 保留 30 个 FP32 norm 权重；连同 A_log 共 60 个 FP32 参数哈希相同；原生对照保留 BF16 autocast | 预填充 160 个点与最终状态逐位一致 |
| 缓存解码相对误差约 0.01116 | 原环境使用 CUDA causal_conv1d_update，桥接强制了 PyTorch 回退；恢复真实 CUDA 绑定 | 16 组预填充+1-token 解码、首组 320 个记录点逐位一致 |
| 静态缓存通过还不足以证明 vLLM 引擎正确 | 接入引擎分配的 30 层 GDN 状态与 10 层分页 KV | 16 组数值、3 组自由生成、4 组边界生成通过；最长 4094+2 |

核对 checkpoint 输入哈希，还须核对加载后的 dtype 与实际后端。GPU 隐藏时能否导入扩展不能证明实际 GPU 使用的卷积一致。完整定位数据保留在 [原日志](../archive/2026-10-09-original-readme.md)。

## 35B 优化：相同权重与配对测量

按顺序尝试：选中 8 个专家批量解包（每层 kernel 16→2）、批量读取缓存调度索引、设备内排序路由权重、30 层 GDN 单 token Graph、40 层 MLP Graph。保留 BF16 舍入、矩阵形状、SiLU、专家累加及原生缓存更新。

同进程阶段使用同一个驻留引擎交替运行，每组 3 对、共 42 次完整请求 CUDA 同步计时；两版均通过 16+7 组数值/生成对照。结果是请求耗时，包含预填充，不应拿输出时间戳估成持续解码吞吐。

| 提示/输出 token | 设备内路由（秒） | 加 GDN Graph（秒） | 加 GDN+MLP Graph（秒） |
|---|---:|---:|---:|
| 中文 21/32 | 3.78 | 3.01 | 1.59 |
| JSON 24/32 | 3.78 | 3.05 | 1.63 |
| Python 21/32 | 3.74 | 3.00 | 1.58 |
| 1024/64 | 7.92 | 6.45 | 3.54 |
| 1055/32 | 4.91 | 4.17 | 2.74 |
| 2111/32 | 5.12 | 4.34 | 2.92 |
| 4094/2 | 2.60 | 2.55 | 2.51 |

各列来自相应阶段的独立配对实验，前后列本身不是同次配对。GDN 阶段相对其同次 eager 对照前六组耗时降低约 14–20%；MLP 阶段相对其同次仅 GDN Graph 对照额外降低约 33–47%。预热/录制在计时前；最终驻留分配约 14,501,812,736 字节，缓存预算不变。

**范围始终是两步 35B 控制产物和固定单请求。** 不能推导完整训练后的能力、122B 速度、共享 Graph 工作区并发安全或正式服务吞吐。源码尚未发布，当前表用于理解优化过程，不能按仓库直接复现该桥接。

## 35B完整8192步产物的自定义推理

R35-8192 与上面的两步 vLLM 控制是不同路线。其 manifest 为 `2a8aba243717e5b0230cc388d65e0f2f9c446bf30dde69581fbfa731f85e0f99`；在一张 5090 完成 640 个逐层和 16 个整模型缓存检查后，五档 Graph 对照正常退出，全部 64 个 token ID 与静态缓存版本一致。

| 上下文 token | Graph 解码 tokens/s | 预填充秒 | 峰值 CUDA allocated 字节 |
|---:|---:|---:|---:|
| 128 | 59.33 | 0.698 | 15,943,207,936 |
| 512 | 58.12 | 0.813 | 15,988,767,744 |
| 4096 | 49.85 | 1.348 | 16,756,948,480 |
| 8192 | 42.25 | 2.435 | 17,674,911,232 |
| 16384 | 32.71 | 4.216 | 19,602,980,352 |

每档仅一个计时样本，固定输出 64 步，测速会越过 EOS；解码吞吐排除预填充与 Graph 录制，峰值包含缓存初始化与录制。全部文本参数和缓冲在 CUDA，无 CPU 权重卸载；视觉模块未物化。此结果不证明能力、长上下文质量或并发服务吞吐。详见[脱敏完成记录](2026-10-09-2156.json)。35B 运行入口尚未发布。

## 122B：仓库入口实际验证

已发布入口在 5090 上重新完成 old/native4095 两版生成与五档 Graph/静态 token ID 一致性。native4095 的 128/512/4K/8K/16K 为约 28.75/28.65/25.84/22.97/19.01 tokens/s，单档一个计时样本，固定输出 64 步，排除预填充和 Graph 录制，即使 EOS 也继续测速。中文生成控制上限 32 token，不是完整回答质量测试。

16K 峰值 CUDA allocated 32,494,375,424 字节，文本权重和缓冲驻留 30,171,940,608 字节，无 CPU 权重卸载。字节与 GiB/GB 口径不同，引用显存时保留原始字节。

完整命令、原始数值和限制见 [122B 说明](../../experimental122/README.md) / [实测 JSON](../../experimental122/native4095-verified-run.json)。四组公开质量均低于原模型。当前没有发布 122B vLLM 插件、并发服务或视觉路径。

曾测试 LUT A/B，约 1.6–2.5% 收益未采用；直接 GEMV 的整模型误差未通过，未放宽阈值。后续优化继续使用相同权重、上下文和输出长度，分别报告预填充/录制/解码、峰值显存、数值误差与能力结果。

## 122B部署优化与显存口径

项目使用者接受当前实验版质量取舍，部署优化以相同 native4095 权重为基准，不修改历史质量分数或把低于原模型改写成质量无损。当前文本权重及缓冲占 30,171,940,608 字节，即约 **28.10 GiB**。

| 上下文 | 峰值 PyTorch allocated | 固定 64-token 解码速度 |
|---|---:|---:|
| 128 | 28.39 GiB | 28.75 tokens/s |
| 4K | 28.91 GiB | 25.84 tokens/s |
| 8K | 29.22 GiB | 22.97 tokens/s |
| 16K | 30.26 GiB | 19.01 tokens/s |

原始字节见[实测 JSON](../../experimental122/native4095-verified-run.json)。allocated 不包括全部 CUDA 上下文和驱动开销；整卡实际占用需另测，不能将其直接当作剩余可用显存。上述单样本速度不包含预填充与录制。

已完成相同 native4095 权重的 27 次实际请求对照：三条自拟中文/数学/代码提示分别为 27/40/39 输入 token，各模式重复三次。生成启用 EOS 停止，但本次全部到达 96-token 上限，不能解释成完整回答。2592 个输出 token ID 全部相同，任务正常退出。原入口构造与生成各做一次准备；单次准备消除重复预填充/录制，跨请求复用则保留同一 Graph 和缓存地址，重置状态后写入新提示。

| 执行方式 | 首 token 中位数 | 9 次串行请求输出吞吐 | 峰值 allocated |
|---|---:|---:|---:|
| 原入口，两次准备 | 6.058 秒 | 10.21 tokens/s | 28.59 GiB |
| 每请求只准备一次 | 2.910 秒 | 15.23 tokens/s | 28.66 GiB |
| 跨请求复用 Graph | 1.524 秒 | 18.99 tokens/s | 28.67 GiB |

吞吐为各模式输出 token 总数除以完整请求耗时总和，包含预填充和该模式需要的录制，排除最初模型加载。复用组包含首次录制；其后 8 次请求约 19.57 tokens/s。模式按固定顺序测试，不是随机交替 A/B；纯解码仍约 28 tokens/s。加载后整卡观察值约 28.70 GiB，复用组请求末观察最大约 29.75 GiB，后者不是全程采样的整卡峰值。原始字节、reserved 和每组限制见[27 次对照记录](2026-10-09-2312.json)。

独立新进程还已完成新增 `run_requests.py` 正向执行并退出 0：加载同一完整产物，三次请求的 288 个输出 token 与原路径完全相同，只录制一个 Graph，复用两次。已发布[常驻请求入口及命令](../../experimental122/README.md#常驻模型与跨请求-graph-复用)，源码身份与证据见[独立 CLI 完成记录](2026-10-09-2316.json)。已验证的是固定缓存容量 1536 的短请求；更长容量需另验。

多请求批处理仍在验证。第一版 batch=2 在预填充阶段被旧归一化模块的单请求形状断言拒绝，尚未产生 batch 吞吐成绩，也未证明显存不足。失败记录保留；第二版针对不超过 4096 的短上下文调用同一原生 RMS 算式，正在进行新对照。当前发布入口仍为串行单 worker，没有并发服务或 vLLM 支持。
