## Graph实际验证到了哪里

使用同一份公开32步权重、同一张RTX 5090，按原路径→Graph→Graph重复→原路径跑四轮，每轮八道原始开发题。
本轮“原路径”指现有的 `decode_rotate`。

- 四轮速度分别为 **9.209 / 13.222 / 12.825 / 9.591 token/s**。
- 每轮生成138个token，其中130个属于首token后的解码计时。
- 两轮原路径合计260个token / 27.67185秒，Graph合计260个token / 19.96838秒；由此得到9.39583和13.02058。
- 前后原路径漂移4.15%，Graph两轮相差约3.00%；较慢Graph仍比较快原路径高33.73%。

Graph只复用48个GDN层的单token执行图，减少每步CPU启动开销。
16个full-attention层与原DynamicCache保留，每次执行复制当前请求的状态。

四轮的输入、生成token、每步完整词表末位置logits、EOS位置及64层最终cache均一致。
前一个仍存活请求的cache也未被新请求修改；1248项冷复制审计通过，计时中新增审计为0。
输入、输出和logits哈希也与[此前公开32步结果](2026-10-20-Q38-step32-fast-portable.json)逐项一致。

原路径和Graph都使用相同BF16计算设置：旧加载器已经禁用 reduced-precision reduction，本轮显式设置保持一致。
没有重新训练或修改权重。

## 显存与计时范围

本轮峰值PyTorch **allocated为8.277 GiB，reserved为13.367 GiB**。
四轮都保留同一批Graph池，所以本轮原路径的reserved值也包含Graph驻留，不能用来代替无图入口的显存需求。
整卡采样最高14,967 MiB；采样值与PyTorch峰值不是同一口径。

速度是batch=1、greedy、每题最多32个新token的短提示热计算结果：

- 包括forward、GDN输入与状态复制、Graph replay、argmax和CUDA同步。
- 排除加载、构图、分词、CPU哈希、EOS处理和输出。
- 构图耗时约7.41秒；身份检查、加载和完整实验合计约376秒。

这组结果没有证明聊天端到端吞吐或首token变快。
本轮Graph的首token计算中位数约0.33–0.35秒，原路径约0.30秒。

## 其余路线为什么没有采用

前四项使用未发布96步候选；最后一项使用公开32步权重。各行比较来自各自匹配实验。

| 路线 | 实际结果 | 本轮结论 |
|---|---|---|
| 缓存16 GiB的BF16权重 | 四轮八题精确一致；合并约快5%，allocated峰值增至21.90 GiB，基线自身漂移7.46% | 收益不稳定，保留原默认路径 |
| 调整解包分块 | 微测更快，但完整四轮八题约慢7.40%；数值一致 | 不采用 |
| 直接对压缩权重做GEMV | 矩阵微测通过；整模型第2个生成步骤超过预设logits误差门限 | 未通过整模型验收 |
| StaticCache与全模型Graph | 两种静态缓存方案均在`static_eager`数值对照阶段失败 | 未进入可接受的Graph性能比较 |
| 仅GDN Graph | 公开32步权重四轮八题精确一致，合并快38.6% | 保留实验结论；便携入口GPU未验证，本轮不发布 |
