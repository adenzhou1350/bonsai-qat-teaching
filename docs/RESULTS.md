## 质量：每条路线只与自己的对照比较

以下是实验中使用的**四组开发评测**。CMMLU 201 题、GSM8K 200 题是本实验的子集；中文与格式是 48 题小面板。HumanEval 使用 164 题，但也属于本项目开发过程中的评测。它们不是官方完整榜单，也不是新打开的独立最终测试。保留测试未打开，完整评分流程与所有输入尚未随教学入口一并公开。

表内直接写通过数 / 总题数，避免把小样本结果包装成额外的精度。未支持的 HumanEval 样本仍计入 164 的分母。不要将不同模型或不同历史运行的 BF16 分数互换。

## HTTP：四客户端合计吞吐，严格 ID 验收未通过

使用同一 native4095 产物，在一张 RTX 5090 上比较原预填充 A 与每 16 个专家分组的预填充 B。顺序为 **A / B / B / A**，每轮新启服务，先热身 8 条，再正式测 64 条。

| 测量条件 | 范围 |
|---|---|
| 并发与样本 | 4 个闭环客户端；8 条固定提示反复使用，正式共 256 条请求，不是 256 道独立任务 |
| 长度与缓存 | 输入不超过 128 token，输出上限 64；总上下文 1536，KV 缓存 896 MiB |
| 生成与输出层 | greedy；未启用 FP32 输出层诊断候选 |
| 计时包含 | HTTP、调度、预填充、解码与序列化 |
| 计时排除 | 模型加载、启动阶段的 Graph 录制和显式热身 |

| 指标 | 原预填充 | 分组预填充 |
|---|---:|---:|
| 四客户端合计输出 tokens/s | 21.01 | 23.30 |
| 相对变化 | — | +10.90% |

每个模式的吞吐按**两轮输出 token 总数 / 两轮客户端墙钟总时间**计算，不取两轮速度的简单平均。它是服务合计值，不能当成每个客户端都有 23.30 tokens/s，也不能拿它与排除预填充的纯解码速率直接比较。

正式测量有 15,040 个输出 token，256 条请求均正常 HTTP 200 / DONE，四个服务排空后退出 0。与旧 CLI 比较，**244 / 256 条请求的完整输出 token 序列相同，12 条不同**；这里的分母是请求数，不是 token 数或答题准确率。四轮差异分别为 4、3、1、4 条，均为中文 docstring 的后段措辞变化。原版和优化版都出现差异，不能把这 12 条全部归因于分组优化。

因此结论是：固定负载下的吞吐观测完成，严格 ID 一致性验收未通过。默认仍用原预填充；未据此给出持续服务、真实业务容量或延迟 SLA 承诺。[完整 HTTP 记录](experiments/2026-10-10-1145-HTTP-observed-ABBA.json)

FP32 输出层是另一个诊断候选：修正后的短程运行中，热身 8 条和正式 64 条与旧 CLI 固定样本的 ID 全部相同，但没有完整四轮性能验收。后来合并输出头的试验在第二个服务中途停止，也没有合并吞吐收益可报告。[FP32 诊断](experiments/2026-10-10-1120-bound-FP32-head-completed.json) · [暂停记录](experiments/2026-10-10-1150-research-paused.json)

## 显存：模型存储不等于运行占用

下面对应短请求部署；GiB 按 `2^30` 字节、MiB 按 `2^20` 字节换算。权重与持久缓冲的存储量、NVML used 和 driver reserved 是不同口径。

| 项目 | 数值 | 含义 |
|---|---:|---|
| CUDA 模型持久存储 | 28.10 GiB | 30,172,726,976 字节，不含全部运行时开销 |
| NVML used 已采样峰值 | 30.64 GiB | HTTP 四轮共 57,036 个采样点中的最大值 |
| NVML driver reserved | 约 0.484 GiB | 驱动单独报告的保留量，不要漏掉或重复算入 used |
| NVML free 已采样最小值 | 740.31 MiB | 该短请求配置测到的余量，不是任意长度的余量保证 |

这些数据支持“指定配置在 32GB 5090 上运行”，不支持“只需 28GB 显存”。采样峰值也不保证捕获所有瞬时峰值。较长输入实验的配置和占用另行记录，不能直接套用这张表的余量。[短请求部署记录](experiments/2026-10-10-0816-prefill16-deployment.json) · [HTTP 采样记录](experiments/2026-10-10-1145-HTTP-observed-ABBA.json)

## CLI：短请求与较长输入分别看

下面是另外两组 CLI A/B/B/A 实验，都比较原预填充与分组预填充。它们没有 HTTP 开销，协议也不同于上面的服务测量。

| 实验 | 固定负载 | 原版 → 分组 | 输出核对 |
|---|---|---|---|
| 短请求 CLI | 每轮 32 请求，4 类提示重复；每轮 1,880 个输出 token | **21.72 → 24.00 输出 tokens/s**（+10.51%） | 四轮共 7,520 个输出 ID 与旧路径相同 |
| 较长输入 CLI | 252 / 503 / 1020 / 1404 输入 token 的 4 类检索提示；每轮 32 请求、25,432 输入 / 104 输出 token | **114.23 → 146.95 输入 tokens/s**（+28.64%） | 四轮 416 个输出 ID 及 EOS 相同 |

第二行的 146.95 是**输入吞吐**，不是生成速度；同一记录中的输出吞吐仅为 0.467 → 0.601 tokens/s。它按请求总时间计算，包含解码等工作，记录中还有 JIT，未单独安排热身，也不是纯预填充 kernel 的速率。128 条检索请求由 4 类自编提示重复而来，全部答对不能证明通用长上下文能力。

短请求 CLI 两版实际均用 896 MiB 缓存；早期摘要把 baseline 标为 1024 MiB 是已发现的元数据错误，原记录与纠正说明保留。三组实验的百分比不能相加，也不代表跨模型或跨业务的统一加速比。[短请求证据](experiments/2026-10-10-0816-prefill16-deployment.json) · [较长输入证据](experiments/2026-10-10-0921-long-input-ABBA.json)

## 复现之前确认边界

- **CPU 教学**：可从公开源码做三值、梯度与恢复检查，按 [Linux CPU 指南](REPRODUCING.md)准备。
- **数据与初始化**：[校准数据课程](../courses/122b/README.md)和 [CPU seed 课程](../courses/122b/seed_cpu/README.md)已发布，仍需原始 BF16 模型及相应资源。
- **固定产物推理**：[CLI / HTTP 指南](../experimental122/README.md)需要另行取得指定 packed 权重与匹配环境，仓库没有模型权重。
- **完整复刻**：公开代码尚不能从原始 122B 权重一路生成、训练并验收同一产物；完整评分流程也尚未随课程发布。T35 的导出不能直接交给 R122 推理入口。

如果增加或引用新结果，先写清模型 / 产物、训练对象、数据分母、硬件、计时范围与失败项，再链接原始记录。历史数据和默认运行入口分别保存；目录整理不改变已测源码或产物身份。
